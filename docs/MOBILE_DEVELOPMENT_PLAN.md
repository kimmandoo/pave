## Baseline and boundaries

Pave has a read-only `mobile_project` tool that inventories bounded workspace subprojects for Swift/Xcode/SwiftPM, Android Gradle, Flutter/Dart and React Native/Expo manifests and suggests commands without executing them. A reported shared `.xcscheme` filename is filesystem evidence only, not proof Xcode can parse/build/test it; candidate tasks, targets and SDK/emulator/device/signing readiness remain unknown. M01 regressions cover nested manifests, truncation, ignored/generated roots, symlink escapes and oversized inputs; M02 regressions and an actual CLI tool-call smoke map shared scheme files to exact project/workspace roots, keep private/missing schemes unknown and do not invoke Xcode.

Preserve `docs/DESIGN_RULES.md`: inspect actual project files and follow local conventions; do not invent toolchains, variants or destinations. Keep reads inside the checked workspace and retain symlink, ignore, size and cancellation bounds. A manifest or package script is untrusted input, not permission to run it. A proposed command is never an executed check. `run_command` and any subprocess that evaluates project code require their existing interactive, **per-command** approval even under `yolo`; headless execution requiring approval fails closed. Never silently install dependencies, fetch packages, boot a device, sign, provision or deploy. Signing, device use, destructive changes and credential access need informed approval for the exact action. Report missing SDKs/targets/devices as unavailable, not as successful builds.

Each slice must deliver one visible behavior, a behavior-level regression with a positive and a misleading/unsafe case, and an actual CLI/tool or PTY smoke covering the changed path. For platform-specific execution, use a real available toolchain and a disposable project/device; if unavailable, leave execution acceptance open rather than substitute a mock for a successful build or device run. Deterministic fixture logs can establish diagnostic parsing, but not a platform's runtime readiness. Do not alter the baseline mobile safety prompt merely to make a test pass. Record resulting contract changes in the design rules, user-facing changes in README/changelog, and nontrivial resolved failures in troubleshooting as usual.

## A — Project evidence and selection

- **M01 — Bounded manifest inventory.** Extend the root-only `mobile_project` evidence scan to bounded workspace subprojects without following symlinks, generated directories or ignored dependency trees. **Depends:** existing workspace traversal. **Accept:** an iOS/Android monorepo reports both manifest paths with explicit scan truncation; a deceptive symlink or oversized manifest supplies neither a trusted stack nor executable command.
- **M02 — Xcode project and scheme map.** From verified `.xcworkspace`/`.xcodeproj` entries and available shared scheme files, report project/workspace and candidate scheme provenance, without inventing a target or destination. **Depends:** M01. **Accept:** a workspace containing two projects reports the corresponding schemes without crossing roots; a missing/private scheme stays unknown.
- **M03 — SwiftPM package map.** Read `Package.swift` as bounded text without evaluating it; identify the package root and existing conventional `Tests/` directories as candidate test roots, not target declarations. **Depends:** M01. **Accept:** a package beside an Xcode project remains a distinct stack; computed/unsupported test targets and SDK requirements stay unknown.
- **M04 — Android module map.** Recognize bounded static literal `include` calls in `settings.gradle`/`.kts`, associate included paths with any observed wrapper script and existing conventional module source/test roots, and never execute Gradle. **Depends:** M01. **Accept:** a multi-module `.kts` map remains scoped to declared modules; dynamic includes, `projectDir` remapping, task variants and missing wrappers stay unresolved.
- **M05 — Flutter package and host map.** Distinguish Flutter apps, packages, plugins and plain Dart from bounded `pubspec.yaml` evidence, and identify existing `ios/` and `android/` host roots. **Depends:** M01. **Accept:** a plugin fixture identifies its host locations; a Dart-only or unreadable pubspec is not labeled a buildable Flutter app.
- **M06 — React Native/Expo script and host map.** Use bounded `package.json` dependency/script evidence and existing lockfiles/native roots to identify RN versus Expo and the project's package-manager choice, without executing scripts or `npx`. **Depends:** M01. **Accept:** two conflicting lockfiles require an explicit choice; an absent declared test script is not offered as runnable.
- **M07 — Mixed-stack selection.** When several credible roots/stacks coexist, return their evidence separately and require an exact workspace subroot and platform before suggesting a focused platform command. **Depends:** M02–M06. **Accept:** a Flutter app's `android/` host and a neighboring Android app do not share a Gradle target; cancellation leaves session/model/draft unchanged.

## B — Focused build and test paths

Every item below distinguishes a **preview** from execution. Discovery commands that evaluate project files are execution, not harmless probes. Reuse the existing command approval/timeout/cancellation path; do not add a parallel shell bypass.

- **M08 — Xcode scheme/destination preflight.** With a selected Xcode root, obtain available schemes/destinations only through an individually approved Xcode command and propose a build/test for an actual choice, with signing disabled only where appropriate. **Depends:** M02, M07. **Accept:** absent Xcode or no matching scheme/destination yields an actionable refusal; an approved disposable project performs one selected non-signing build/test and records the actual exit.
- **M09 — SwiftPM focused tests.** For a selected package and actual test target/filter, preview then run the smallest supported SwiftPM test command under separate approval. **Depends:** M03, M07. **Accept:** an available package runs the selected tests; a nonexistent filter, unavailable `swift` or canceled approval never becomes a reported pass.
- **M10 — Gradle task/variant preflight.** Treat `gradlew` and build scripts as untrusted executable code: only an approved task listing may establish concrete module/variant tasks, and a second approval runs the chosen focused build/test. **Depends:** M04, M07. **Accept:** a disposable multi-variant project runs its selected task and preserves the exit status; a nonexistent variant and blocked/offline dependencies remain failures, not `assembleDebug` fallbacks.
- **M11 — Flutter analysis and tests.** Preview `flutter analyze` or a workspace-relative targeted `flutter test` for the selected Flutter project; execute only after approval, without automatic `pub get` or iOS build. **Depends:** M05, M07. **Accept:** a disposable Flutter project exercises one real focused check when the SDK exists; a Dart-only project or absent SDK gets no claimed Flutter result.
- **M12 — React Native/Expo test scripts.** Preview an existing project-declared test/lint script with the selected package manager; explain that npm/yarn/pnpm scripts can execute arbitrary project code. **Depends:** M06, M07. **Accept:** an approved disposable RN/Expo fixture runs the selected script and reports its real exit; an undeclared script or ambiguous lockfile never triggers `npx`/package installation.

## C — Source-linked failure diagnosis

Read bounded tool output; strip terminal controls, redact secrets, resolve reported paths only under the selected workspace and retain raw error context. Diagnosis may suggest the next test but must not rewrite source or claim a build was run. Distinct formats make these independently shippable.

- **M13 — Xcode/Swift diagnostics.** Map Swift compiler/test failure paths and line/column to the selected Xcode/SwiftPM source, preserving scheme and tool exit provenance. **Depends:** M08 or M09. **Accept:** a captured failing command highlights an in-root Swift line; an external or malformed path remains quoted text, never a clickable workspace edit.
- **M14 — Gradle/Kotlin diagnostics.** Map Gradle task failure and Kotlin/Java source locations to the selected module/variant, without reporting the tail of a partial log as a passing build. **Depends:** M10. **Accept:** a failing multi-module fixture names the real task and file; a stack trace mentioning a different module cannot switch the selected root.
- **M15 — Flutter/Dart diagnostics.** Map analyzer/test failures to bounded Dart file locations and retain the actual Flutter command exit. **Depends:** M11. **Accept:** a widget-test failure points to its own package file; truncated output is labeled incomplete rather than summarized as a successful test.
- **M16 — React Native/Metro diagnostics.** Map JS/TS test or Metro failures to verified project-relative files without treating a dependency stack frame or ANSI escape sequence as an editable source path. **Depends:** M12. **Accept:** a failing declared script identifies the project file and exact exit; `node_modules` and an external path remain untrusted context.

## D — Devices and mobile-specific change safety

Inventory is not authorization to boot, install, launch, sign or deploy. Device identifiers, signing material and local paths need private, bounded presentation; no device/simulator is assumed in CI.

- **M17 — Apple simulator inventory.** On a supported macOS host, list available simulator runtimes/devices through an explicitly approved read-only command; associate them with a chosen Xcode scheme without booting one. **Depends:** M02, M07. **Accept:** a real simulator listing shows only available compatible choices; no Xcode/runtime reports unavailable and performs no boot.
- **M18 — Android emulator/device inventory.** Through explicitly approved commands, list available AVDs/ADB devices and distinguish offline/unauthorized states without installing an SDK or choosing a serial implicitly. **Depends:** M04, M07. **Accept:** a real available AVD or disposable emulator is enumerated; an offline/unauthorized device is not offered as ready to test.
- **M19 — iOS simulator test.** Require the user to pick a verified simulator, preview exact scheme/destination/build effects, then request approval for the one Xcode test command. Do not sign or deploy to a physical device. **Depends:** M08, M17. **Accept:** a real simulator test on a disposable app reports its exit and target; cancel/no compatible simulator causes zero test invocation and no false pass.
- **M20 — Android emulator test.** Require an explicitly selected ready emulator and a verified module/test task, then approve that exact Gradle test/instrumentation action; install/boot is a distinct approved action, never an implicit fallback. **Depends:** M10, M18. **Accept:** a disposable app test reaches the selected emulator and reports the actual result; offline/no device causes no install/test attempt.
- **M21 — iOS signing and entitlement diff guard.** Before an edit to entitlements, capabilities, bundle ID, deployment target or signing configuration, present the exact affected files and security/deployment implications; never fetch private keychain identities or automatically sign. **Depends:** M02. **Accept:** a fixture adding an entitlement gets a distinct review/approval and denied changes leave bytes untouched; ordinary Swift-only edits remain ordinary workspace edits.
- **M22 — Android permissions and SDK diff guard.** Before an edit to `AndroidManifest.xml`, SDK levels or sensitive Gradle signing settings, present the exact permission/API/build effect without exposing keystore material. **Depends:** M04. **Accept:** a fixture adding a runtime permission requires a distinct review and denial preserves the original; a normal Kotlin edit does not become a deployment approval.
- **M23 — Flutter platform-channel consistency.** For an edited Dart method channel and its existing iOS/Android host handlers, identify the actual matching names/argument shapes and select focused tests without generating a missing bridge or modifying native signing settings. **Depends:** M05, M11. **Accept:** a disposable plugin mismatch is surfaced at both source locations; a Dart-only package is not assigned an imaginary native handler.
- **M24 — React Native native-module/Expo configuration consistency.** Connect an edited JS/TS native-module call or Expo config value only to verified iOS/Android declarations and propose the existing declared tests; never run prebuild or install packages implicitly. **Depends:** M06, M12. **Accept:** a fixture mismatch names the actual JS and native/config files; managed Expo without native folders is reported as such rather than given fabricated Xcode/Gradle files.
